30초 구조 요약
사용자가 터미널에서 명령을 입력하면 __main__.py가 프로그램을 시작하고, cli.py가 명령과 입력을 받습니다. 실제 규칙 검사는 service.py, 파일 읽기·쓰기는 repository.py가 맡습니다. 거래 모양은 models.py의 Transaction이 정의하고, CSV 교환은 csv_service.py, 공통 오류 처리는 decorators.py의 safe_entry가 맡습니다.

핵심 Python 개념

코드를 외우기보다 “왜 썼는지” 이해하는 부분입니다.

Generator · yield

쉬운 뜻: 창고의 물건을 한꺼번에 바닥에 쏟지 않고 컨베이어 벨트로 하나씩 보내는 방식입니다.

for line in file:
    ...
    yield Transaction(...)

왜 사용? transactions.jsonl 전체를 한 번에 메모리에 올리지 않고 한 줄씩 처리하기 위해서입니다.

정확한 한계: search는 파일은 한 줄씩 읽지만 최신순 출력을 위해 일치 결과를 deque에 모읍니다.

Decorator · @safe_entry

쉬운 뜻: 여러 방마다 경비원을 두는 대신 건물 입구에 안전요원 한 명을 두는 것입니다.

@safe_entry
def main() -> None:
    run_cli()

왜 사용? KeyboardInterrupt, EOFError, ValueError, OSError를 진입점에서 공통 형식으로 안내하고 traceback 노출을 막기 위해서입니다.

Type Hint · 타입 힌트

쉬운 뜻: 함수 입구에 “여기는 문자열을 넣고, 결과는 정수 또는 없음이 나옵니다”라는 표지판을 붙이는 것입니다.

def get_budget(self, month: str) -> int | None:

중요: 타입 힌트는 실행 중 강제로 막는 장치가 아니라 사람과 IDE가 코드를 이해하고 실수를 찾기 쉽게 하는 계약 표시입니다.

dataclass · Transaction

쉬운 뜻: 거래 한 장의 “정해진 서식”입니다.

id, type, date, amount, category, memo, tags를 같은 모양으로 묶어 Service와 Repository가 함께 사용합니다.

거래가 10만 건으로 늘어나면?

현재 구조의 장점과 한계를 구분해서 설명합니다.

현재 방식10만 건에서 생길 수 있는 문제개선 방향
search가 파일 처음부터 끝까지 확인검색 1회마다 최대 10만 건 비교날짜/카테고리 인덱스, SQLite
검색 결과를 deque에 모아 최신순 출력일치 결과가 많으면 그만큼 메모리 증가limit·pagination, 역방향 읽기, DB ORDER BY + LIMIT
update/delete 시 전체 JSONL 재작성데이터가 많을수록 수정 1건에도 전체 파일 쓰기SQLite의 id 기반 UPDATE/DELETE
왜 지금은 파일 구조를 사용하나?
이 프로그램은 파일 입출력, JSONL, Generator, Service/Repository 구조를 학습하기 위한 작은 콘솔 서비스입니다. 현재 규모에서는 구조가 단순하고 학습 목적에 잘 맞습니다. 데이터가 크게 늘어나는 시점에는 Repository만 데이터베이스 방식으로 교체하는 방향이 자연스럽습니다.
