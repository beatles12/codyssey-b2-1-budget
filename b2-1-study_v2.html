B2-1 평가표 1~4 대응 노트

평가표 사진의 항목 1~4를 질문 순서대로 정리했다. 각 칸에서 “무엇을 보여주고, 어떻게 설명하며, 현재 코드가 어디까지 하는지”를 확인한다.

검토 기준: 이 작업 공간의 budget_refactor_stage/budget_app, budget_refactor_stage/README.md, 평가표 사진. 2026-09-17 확인.

먼저 읽기1 기능·실행2 설계·안전3 Python 개념4 선택·한계마지막 점검

먼저 읽기

작업 위치: PowerShell에서 budget_refactor_stage 폴더를 연 뒤 명령을 실행한다. 아래의 python은 일반적인 Python 설치 환경의 명령이다. 이 문서를 만든 환경에는 python 명령이 등록되지 않아, 자동 테스트와 오류 종료 확인에는 번들 Python을 사용했다.

연습 데이터: 시연 명령은 기본 data 대신 --data-dir study_demo를 쓴다. 이 옵션은 명령 이름 앞에 놓는다. 실제거래ID는 예시 글자이므로 목록에서 출력된 ID로 바꾼다.

표시 뜻: “코드·테스트 확인”은 현재 코드와 자동 테스트를 대조했다는 뜻이다. “부분 충족”은 중요한 제한이 있다. 예시 화면의 ID와 건수는 연습 데이터에 따라 달라진다.

사용자 명령→__main__.py · @safe_entry→cli.py→Service / CsvService→Repository→JSONL 3종

항목 1 · 기능 동작과 실제 시연

평가표의 일곱 질문을 차례로 확인한다.

1-1 add / list / search / summary / export / import / update / delete 부분 충족

평가자가 보는 것
요구한 여덟 명령이 동작하는지, 거래 ID와 월별 요약이 실제 데이터와 맞는지.
30초 답변
“CLI가 명령을 골라 Service에 맡깁니다. 거래 추가·조회·검색·요약·수정·삭제는 TransactionService가 처리하고, CSV 입출력은 CsvService가 담당합니다. 파일 읽기와 저장은 Repository가 합니다.”
보여줄 코드/파일
budget_app/cli.py의 build_parser(), run_cli(); service.py의 TransactionService; csv_service.py. README.md 3·8·9절.
실제 실행 명령
python -m budget_app --help
python -m budget_app --data-dir study_demo add
python -m budget_app --data-dir study_demo list --limit 3
python -m budget_app --data-dir study_demo search --category food
python -m budget_app --data-dir study_demo summary --month 2026-09 --top 3
python -m budget_app --data-dir study_demo export --out study-demo.csv --month 2026-09
python -m budget_app --data-dir study_demo import --from study-demo.csv
python -m budget_app --data-dir study_demo update --id 실제거래ID
python -m budget_app --data-dir study_demo delete --id 실제거래ID
마지막 두 줄의 ID는 목록에서 복사해 바꾼다. add와 update는 화면의 질문에 답한다. delete는 y를 입력해야 삭제된다.
정상 화면
[저장 완료] id=..., 목록의 거래와 ID, 검색 결과, [월별 요약], [완료] study-demo.csv (N records), [완료] imported=N, skipped=N, [수정 완료], [삭제 완료]가 단계별로 보인다.
꼬리질문
“검색은 어떤 조건을 결합하나요?” → 기간·카테고리·타입·메모 부분 문자열·태그를 함께 거를 수 있다.
주의점
CSV를 내보낸 뒤 같은 파일을 다시 가져오면 새 ID로 중복 거래가 생긴다. 따라서 위 명령 전체를 한 데이터 폴더에서 연속 실행할 때 요약 건수는 달라질 수 있다. update는 옵션으로 값을 바꾸는 방식이 아니라 대화형 입력이다.
현재 코드 충족 여부
여덟 명령의 분기와 서비스 구현은 확인했다. 자동 테스트는 12개 통과. 단, 이 작업에서 여덟 명령을 모두 수동으로 끝까지 시연한 결과까지 확인한 것은 아니다.

1-2 재실행 뒤 영구 저장 · 파일 3종 부분 충족

평가자가 보는 것
프로그램을 종료했다가 다시 실행해도 거래·카테고리·예산이 유지되는지와 저장 파일 세 종류.
30초 답변
“Repository가 거래는 transactions.jsonl, 카테고리는 categories.jsonl, 예산은 budgets.jsonl에 저장합니다. 다음 실행에서 같은 --data-dir을 쓰면 파일을 다시 읽습니다.”
보여줄 코드/파일
repository.py의 세 Repository, cli.py:run_cli(), README.md 6·7절.
실제 실행 명령
python -m budget_app --data-dir study_demo add
python -m budget_app --data-dir study_demo list --limit 3
python -m budget_app --data-dir study_demo budget set --month 2026-09 --amount 600000
python -m budget_app --data-dir study_demo budget get --month 2026-09
Get-ChildItem study_demo -Filter *.jsonl | Select-Object Name
정상 화면
두 번째 실행의 목록에 앞서 추가한 거래가 보이고 예산 조회에 2026-09 예산: 600,000원이 나온다. 거래·카테고리·예산을 모두 저장한 뒤 세 파일명이 보인다.
꼬리질문
“첫 실행 직후 세 파일이 모두 있나요?” → 아니다. 카테고리 파일은 기본 목록 생성 시 만들어지고 거래·예산 파일은 해당 값을 처음 저장할 때 만들어진다.
주의점
같은 폴더로 다시 실행해야 보인다. 세 파일의 즉시 자동 생성을 주장하면 코드와 다르다.
현재 코드 충족 여부
세 저장 경로와 재실행 읽기 구조 확인. 파일 세 개가 첫 실행부터 만들어진다는 뜻으로는 부분 충족.

1-3 category add / list / remove · 사용 중 삭제 코드·테스트 확인

평가자가 보는 것
카테고리 추가·목록·삭제, 거래가 쓰는 카테고리의 삭제 차단.
30초 답변
“CategoryService가 중복과 존재 여부를 확인합니다. 삭제할 때는 거래 파일도 훑어서 사용 중이면 막습니다. 기존 거래의 카테고리 의미를 지키기 위해서입니다.”
보여줄 코드/파일
service.py:CategoryService.remove_category(), repository.py:CategoryRepository, 관련 자동 테스트 2개.
실제 실행 명령
python -m budget_app --data-dir study_demo category list
python -m budget_app --data-dir study_demo category add
python -m budget_app --data-dir study_demo category remove
추가에서는 새 이름을 입력한다. 삭제에서는 화면에 나오는 카테고리 번호를 입력한다.
정상 화면
[추가 완료] 이름; 목록에 이름이 표시된다. 미사용 항목 삭제는 [삭제 완료] 이름. 사용 중인 항목 삭제는 [입력 오류] 사용 중인 카테고리는 삭제할 수 없습니다.와 힌트.
꼬리질문
“어떻게 사용 여부를 아나요?” → TransactionRepository.iter_transactions()로 거래를 하나씩 확인한다.
주의점
삭제 차단은 거래가 실제로 해당 카테고리를 사용 중일 때만 시연된다. 미리 그 카테고리로 거래를 추가한다.
현재 코드 충족 여부
세 명령과 사용 중 삭제 차단 로직 및 테스트 확인.

1-4 budget set 저장 · summary 사용률/초과 코드·테스트 확인

평가자가 보는 것
월 예산 저장, 재조회, 지출이 있는 달의 사용률과 초과 또는 남은 금액.
30초 답변
“BudgetService가 월과 양수 예산을 검증해 저장합니다. summary에서 구한 총지출을 BudgetService에 넘겨 사용률 지출 ÷ 예산 × 100과 남은 금액을 계산합니다.”
보여줄 코드/파일
service.py:BudgetService.get_budget_status(), cli.py의 summary·budget 분기, repository.py:BudgetRepository.
실제 실행 명령
python -m budget_app --data-dir study_demo budget set --month 2026-09 --amount 10000
python -m budget_app --data-dir study_demo budget get --month 2026-09
python -m budget_app --data-dir study_demo summary --month 2026-09
정상 화면
[예산 저장 완료] 2026-09 = 10,000원과 예산 조회 결과. 해당 월 거래가 있으면 summary에 예산 사용률: ...%와 남은 예산 또는 예산 초과가 보인다.
꼬리질문
“예산과 지출이 정확히 같으면?” → spent > budget일 때만 초과이므로 남은 예산 0원이다.
주의점
거래가 없는 달은 CLI가 데이터 없음을 출력하고 바로 돌아가므로 예산을 설정했어도 그 summary 화면에는 예산 현황이 나오지 않는다.
현재 코드 충족 여부
예산 저장·조회·계산 및 테스트 확인. 거래 없는 달의 표시 제한은 설명해야 한다.

1-5 CSV 스키마 · UTF-8 · 헤더·컬럼 부분 충족

평가자가 보는 것
내보내기/가져오기가 명시한 여섯 열 date,type,category,amount,memo,tags와 UTF-8 헤더를 쓰는지.
30초 답변
“CsvService는 csv.DictWriter로 여섯 열 헤더를 쓰고 UTF-8로 저장합니다. 가져올 때 DictReader로 필수 열이 있는지 검사하고, 각 행을 거래 규칙으로 검증합니다.”
보여줄 코드/파일
csv_service.py:CSV_FIELDNAMES, export_transactions(), import_transactions(); README.md 8~10절.
실제 실행 명령
python -m budget_app --data-dir study_demo export --out study-demo.csv --month 2026-09
Get-Content study-demo.csv -Encoding utf8 -TotalCount 2
python -m budget_app --data-dir study_import import --from study-demo.csv
정상 화면
파일 첫 줄은 date,type,category,amount,memo,tags; 내보내기는 [완료] study-demo.csv (N records), 가져오기는 [완료] imported=N, skipped=0 형태.
꼬리질문
“열 순서가 달라도 되나요?” → 가져오기는 열 이름으로 찾고 필수 이름 존재를 검사하므로 순서가 달라도 처리할 수 있다. 내보내기 순서는 코드에 정한 순서다.
주의점
UTF-8 디코딩과 필수 열은 확인하지만, 정확히 여섯 열만 허용하지는 않는다. 추가 열이 있어도 무시될 수 있다. BOM이 붙은 utf-8-sig 파일은 현재 첫 헤더명과 충돌할 수 있다.
현재 코드 충족 여부
정해진 여섯 열로 export하고 필수 열을 검사한다. 추가 열 거부까지 포함한 엄격한 스키마 검증은 없음.

1-6 잘못된 입력/파일 오류 · 메시지와 힌트 부분 충족

평가자가 보는 것
일반적인 오류에서 긴 traceback 대신 원인과 해결 힌트가 보이는지.
30초 답변
“진입점의 @safe_entry가 입력 오류와 파일 오류를 받아 안내 문구로 바꿉니다. 서비스는 규칙 위반 때 ValueError를 올리고, 진입점은 원인과 다시 확인할 힌트를 출력합니다.”
보여줄 코드/파일
decorators.py:safe_entry(), __main__.py, service.py의 검증, cli.py:parse_amount().
실제 실행 명령
python -m budget_app --data-dir study_demo search --type wrong
python -m budget_app --data-dir study_demo import --from no-such-file.csv
정상 화면
첫 명령은 [입력 오류] 검색 타입은 income 또는 expense만 가능합니다.와 [힌트] 입력 형식과 값을 확인한 뒤 다시 실행해주세요.; 두 번째는 파일을 찾을 수 없다는 입력 오류와 같은 힌트.
꼬리질문
“모든 예외를 가리나요?” → 아니다. 데코레이터가 명시한 KeyboardInterrupt, EOFError, ValueError, OSError 범위다.
주의점
예를 들어 손상된 JSONL의 json.JSONDecodeError는 ValueError의 하위형이라 처리되지만, 모든 뜻밖의 프로그래밍 오류까지 사용자 메시지로 바꾼다고 주장하지 않는다. argparse 옵션 오류는 자체 형식으로 종료한다.
현재 코드 충족 여부
대표 입력·파일 오류 처리 확인. 모든 가능한 오류를 통일한다고 주장할 수는 없음.

1-7 오류 때 0이 아닌 종료 코드 실행 확인

평가자가 보는 것
실패 명령 뒤 종료 코드가 0이 아닌지.
30초 답변
“정상 실행은 종료 코드 0이고, safe_entry가 처리한 오류는 SystemExit(1)로 끝납니다. PowerShell에서는 바로 다음 줄에 $LASTEXITCODE를 보면 확인할 수 있습니다.”
보여줄 코드/파일
decorators.py 마지막의 raise SystemExit(1), __main__.py의 적용 위치.
실제 실행 명령
python -m budget_app --data-dir study_demo search --type wrong
$LASTEXITCODE
정상 화면
오류 메시지·힌트 다음에 1. 이번 작업의 번들 Python 직접 실행에서도 종료 코드 1을 확인했다.
꼬리질문
“왜 0과 1을 구분하나요?” → 다른 프로그램이나 자동화가 성공/실패를 구분하기 위해서다.
주의점
$LASTEXITCODE는 실패 명령 바로 다음에 확인한다. CSV의 깨진 행을 건너뛰고 명령 자체가 정상 완료되면 현재 구현은 종료 코드 0이다.
현재 코드 충족 여부
대표 오류 경로 실행 확인. CSV 부분 성공의 종료 코드는 실패로 분류하지 않음.

항목 2 · 모듈과 클래스 책임, 파일 안전성

파일을 나눈 이유를 “누가 무엇을 결정하는가”로 설명한다.

2-1 3개 이상 모듈의 책임 코드 확인

평가자가 보는 것
코드가 세 모듈 이상으로 나뉘고 경계가 실제 역할과 맞는지.
30초 답변
“cli.py는 명령과 화면 입출력, service.py는 검증과 계산, repository.py는 JSONL 저장을 맡습니다. models.py는 거래 모양, csv_service.py는 CSV 교환, decorators.py는 공통 오류 안내입니다.”
보여줄 코드/파일
budget_app/ 파일 목록, README.md 11절, 각 파일 상단의 클래스·함수.
실제 실행 명령
Get-ChildItem budget_app -Filter *.py | Select-Object Name
python -m budget_app --help
정상 화면
모듈 파일명이 보이고 도움말에 명령 목록이 나온다.
꼬리질문
“CSV가 Repository가 아닌 이유는?” → JSONL 영구 저장과 CSV 교환의 입력 형식·검증 절차가 달라 별도 서비스로 뒀다.
주의점
cli.py가 Repository를 직접 만들고 update 때 find_by_id()도 직접 부른다. 모든 의존성이 완전히 단방향으로만 흐른다고 말하지 않는다.
현재 코드 충족 여부
여섯 기능 모듈과 진입점 확인. 역할은 분리됐으나 CLI의 직접 Repository 접근이 일부 남아 있다.

2-2 2개 이상 클래스의 책임 경계 부분 충족

평가자가 보는 것
클래스가 이름만 다른 빈 껍데기가 아니라 각각 구분된 책임을 갖는지.
30초 답변
“Transaction은 거래 한 건의 데이터 모양입니다. TransactionService는 거래 규칙과 계산을 담당하고, TransactionRepository는 파일에 읽고 씁니다. 카테고리와 예산도 Service가 규칙, Repository가 저장을 맡습니다.”
보여줄 코드/파일
models.py:Transaction, service.py의 세 Service, repository.py의 세 Repository, csv_service.py:CsvService.
실제 실행 명령
python -m budget_app --data-dir study_demo category list
python -m budget_app --data-dir study_demo budget get --month 2026-09
정상 화면
카테고리 목록과 예산 또는 설정된 예산 없음이 보인다. 각 결과가 Service→Repository를 거친다.
꼬리질문
“카테고리 사용 중 여부는 어느 클래스가 결정하나요?” → CategoryService가 TransactionRepository를 조회해 결정한다.
주의점
거래 TransactionService._validate_transaction_input()은 카테고리의 등록 여부를 검사하지 않는다. CLI 번호 선택과 CSV 가져오기에서는 등록 여부를 확인하지만 서비스를 직접 부르면 미등록 카테고리도 저장할 수 있다.
현재 코드 충족 여부
클래스 수와 핵심 책임 분리는 충족. 카테고리 등록 검증이 모든 진입 경로에 일관되게 적용되는 구조는 아님.

2-3 파일 기반 update / delete 안전 처리 부분 충족

평가자가 보는 것
원본 파일을 수정하다가 중간에 잘라먹지 않도록 하는 흐름과 없는 ID 처리.
30초 답변
“Service가 ID 존재와 수정 뒤 값을 확인합니다. Repository는 원본을 읽어 .tmp에 전체 거래를 다시 쓰고, 목표 ID가 있었을 때만 replace()로 원본과 교체합니다. 없는 ID면 임시 파일을 지우고 실패를 알립니다.”
보여줄 코드/파일
service.py:update_transaction()·delete_transaction(), repository.py:update_by_id()·delete_by_id().
실제 실행 명령
python -m budget_app --data-dir study_demo update --id 실제거래ID
python -m budget_app --data-dir study_demo delete --id 없는ID
$LASTEXITCODE
python -m budget_app --data-dir study_demo list --limit 3
정상 화면
수정 뒤 [수정 완료]. 없는 ID를 delete할 때는 먼저 y를 입력하면 [입력 오류] 해당 id의 거래를 찾을 수 없습니다., 종료 코드 1. 목록에서 기존 거래가 남아 있다.
꼬리질문
“왜 파일 전체를 다시 쓰나요?” → JSONL 한 줄의 길이가 달라질 수 있어 가운데 한 건을 제자리에서 안전하게 고치기 어렵다.
주의점
replace()는 정상 완료한 임시 파일로 교체하는 장점이 있지만, 동시 실행·전원 차단·임시 파일 쓰기 실패까지 완전 보장하지는 않는다. 임시 파일 쓰기 중 예외가 나면 정리용 finally가 없어 .tmp가 남을 수 있다. CategoryRepository.remove는 이 임시 파일 방식을 쓰지 않는다.
현재 코드 충족 여부
거래 update/delete의 임시 파일 재작성과 없는 ID 보호 확인. 완전한 트랜잭션·동시성 안전성은 없음.

3-1 list / search의 제너레이터 스트리밍 부분 충족

평가자가 보는 것
yield가 실제 읽기에 쓰이는지, list와 search의 메모리 특성을 정확히 설명하는지.
30초 답변
“Generator는 데이터를 한 번에 목록으로 만들지 않고 필요할 때 하나씩 내보내는 방식입니다. Repository의 iter_transactions()가 JSONL을 한 줄씩 읽어 yield합니다. list는 deque(maxlen=limit)로 최근 N건만 남깁니다. search도 한 줄씩 읽지만 최신순을 위해 일치한 결과를 모두 모은 뒤 내보냅니다.”
보여줄 코드/파일
repository.py:iter_transactions(), service.py:list_transactions()·search_transactions(), README.md 12절.
실제 실행 명령
python -m budget_app --data-dir study_demo list --limit 3
python -m budget_app --data-dir study_demo search --category food
정상 화면
list는 최대 3건을 최근 추가 순서의 역순으로 보여준다. search는 일치 거래를 역순으로 보여준다.
꼬리질문
“search도 메모리가 항상 일정한가요?” → 아니다. matches = deque()에 일치 결과가 쌓여 결과 수만큼 메모리가 든다.
주의점
여기서 “최신순”은 파일에 추가된 순서의 역순이다. 거래 날짜를 정렬하는 코드는 없다. list_transactions()의 반환형은 Generator가 아니라 list[Transaction]이다.
현재 코드 충족 여부
파일 읽기 Generator와 list의 제한 메모리 확인. search의 결과 전체 버퍼링 때문에 완전한 끝단 스트리밍은 아님.

3-3 Type Hint 실제 예와 도움 코드 확인

평가자가 보는 것
입력과 반환 타입을 코드로 집어 설명하고 효용과 한계를 구분하는지.

“Type Hint는 값의 예상 모양을 적는 표시입니다. get_budget(self, month: str) -> int | None은 월을 문자열로 받고, 예산 숫자 또는 미설정 상태인 None을 돌려준다는 뜻입니다. 읽기와 도구 검사에 도움을 주지만 실행 때 타입을 자동 강제하지는 않습니다.”

꼬리질문
“int | None을 왜 쓰나요?” → 값이 없을 가능성을 호출자에게 알려 분기 처리를 잊지 않게 한다.
주의점

현재 코드 충족 여부
실제 함수 시그니처에서 확인.

4-1 JSONL vs CSV 선택 이유 코드 확인

평가자가 보는 것
두 형식의 장단점을 비교하고 이 프로그램에서 고른 근거.
30초 답변
“내부 저장은 JSONL입니다. 거래 한 건이 한 줄이라 순서대로 읽기 쉽고 tags 목록을 그대로 표현할 수 있습니다. CSV는 표로 열기 쉽고 다른 프로그램과 주고받기 좋아 import/export에 씁니다. 대신 CSV의 tags는 쉼표 문자열로 바꿔야 하고, JSONL은 표로 보기 불편합니다.”
보여줄 코드/파일
repository.py:_write_json_line()·iter_transactions(), csv_service.py:CSV_FIELDNAMES·tags_text, README.md 18절.
실제 실행 명령
Get-Content study_demo\transactions.jsonl -TotalCount 1
Get-Content study-demo.csv -Encoding utf8 -TotalCount 2
정상 화면
JSONL의 한 줄은 키·값과 "tags":[...]를 포함하고 CSV 첫 줄은 여섯 열 이름이다.
꼬리질문
“JSONL도 한 줄씩 읽을 수 있나요?” → 가능하다. CSV 역시 행별로 읽을 수 있다. 둘의 차이는 주로 구조 표현과 교환 편의다.
주의점
JSONL이라고 검색·수정이 저절로 빨라지는 것은 아니다. 이 코드는 검색 시 파일을 순회한다.
현재 코드 충족 여부
내부 JSONL / 교환 CSV 구현과 README 설명 확인.

4-2 거래 10만 건의 병목과 개선 코드 확인 · 대규모 실측 없음

평가자가 보는 것
어디가 느려지고 메모리를 쓰는지, 어떤 순서로 고칠지.
30초 답변
“10만 건이면 검색·요약은 파일을 전부 읽을 수 있어 시간이 늘어납니다. search는 일치한 결과를 모아 메모리도 늘고, update/delete는 전체 파일을 다시 씁니다. 먼저 실제 소요 시간을 측정하고, 규모가 계속 커지면 SQLite의 ID·날짜·카테고리 인덱스와 페이지 조회로 옮기겠습니다.”
보여줄 코드/파일
service.py:search_transactions()·summarize_month(), repository.py:update_by_id()·delete_by_id(), README.md 19절.
실제 실행 명령
Measure-Command { python -m budget_app --data-dir study_demo search --category food | Out-Null }
python -m budget_app --data-dir study_demo list --limit 3
정상 화면
Measure-Command의 시간 정보와 최대 3건 목록. 이것은 현재 연습 데이터의 시간이며 10만 건 성능 증거는 아니다.
꼬리질문
“Generator면 10만 건 문제도 끝나나요?” → 아니다. 읽는 메모리를 아껴도 파일 전체 순회 시간과 search 결과 버퍼, 전체 재작성 비용은 남는다.
주의점
10만 건 벤치마크를 실행하지 않았다. list --limit 3도 출력은 3건이지만 현재 구현은 파일 전체를 순회한다.
현재 코드 충족 여부
병목 위치는 코드로 확인. 인덱스·SQLite·페이지 조회는 아직 개선안이다.

4-3 깨진 CSV 행과 사용자 신뢰: 부분 성공·롤백·리포트 부분 충족

평가자가 보는 것
정상 행과 잘못된 행이 섞이면 무엇이 저장되고, 사용자가 결과를 믿고 대조할 수 있는지.
30초 답변
“현재는 행마다 검증해 정상 행은 바로 저장하고, 잘못된 행은 건너뜁니다. 끝나면 imported와 skipped 건수를 보여주는 부분 성공 방식입니다. 전체 롤백과 행 번호별 오류 리포트는 아직 없습니다. 신뢰를 높이려면 먼저 전 행 검증·미리보기, 오류 행 번호와 이유, 가져오기 전후 건수 비교, 필요하면 전체 취소 모드를 추가하겠습니다.”
보여줄 코드/파일
csv_service.py:import_transactions()의 DictReader·try/except·두 카운터, cli.py의 결과 출력, README.md 9절.
실제 실행 명령
$csvText = @'
date,type,category,amount,memo,tags
2026-09-15,expense,food,1200,정상,meal
2026-09-16,expense,food,0,잘못된 금액,
'@
[System.IO.File]::WriteAllText((Join-Path (Get-Location) 'study-mixed.csv'), $csvText, [System.Text.UTF8Encoding]::new($false))
python -m budget_app --data-dir study_import import --from study-mixed.csv
python -m budget_app --data-dir study_import list --limit 5
위 명령은 PowerShell에서 CSV를 BOM 없는 UTF-8로 만든다. study_import 폴더가 이미 사용 중이면 목록의 총건수는 달라진다.
정상 화면
처음 실행한 빈 연습 폴더라면 [완료] imported=1, skipped=1; 목록에는 정상 행 한 건이 남는다. 같은 파일을 다시 가져오면 중복 거래가 생긴다.
꼬리질문
“중간에 파일 전체 오류가 나면 앞서 저장한 행은 되돌아오나요?” → 아니다. 한 행씩 즉시 추가하므로 자동 롤백은 없다. “어느 줄이 왜 빠졌나요?” → 현재 화면만으로는 알 수 없다.
주의점
현재 코드는 잘못된 행마다 ValueError/TypeError/KeyError를 잡아 건너뛰지만, 행 번호·사유를 기록하지 않는다. skipped > 0이어도 명령은 정상 종료한다. 대조 리포트, 미리보기, 롤백, 중복 방지는 미구현이다.
현재 코드 충족 여부
부분 성공과 건수 요약은 구현. 사용자 신뢰에 필요한 상세 리포트·전체 롤백·전후 비교는 구현되지 않음.

마지막 점검

말로 반드시 구분: 구현된 것 / 코드로 추론한 것 / 실제 실행해 확인한 것 / 앞으로 개선할 것.
