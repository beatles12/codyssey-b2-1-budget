기능과 실제 실행

기본 data 폴더에서 거래·카테고리·예산·CSV·오류 처리를 확인한다.

1-1거래 기능: add · list · search · summary · update · delete · export · import

명령을 실행할 때마다 CLI가 입력을 받고, Service가 규칙을 검사하며, Repository가 파일을 읽고 쓴다. 아래 순서는 예산과 카테고리 기능도 함께 이어서 확인한다.

01 · 거래 추가

날짜에 20233333 입력 → 즉시 [입력 오류]와 힌트 확인 → 날짜만 2026-09-15로 다시 입력 → 종류 2 → food 번호 → 금액 15000 → 메모 점심 → 태그 meal.

python -m budget_app add

잘못된 날짜에서는 다음 항목으로 넘어가지 않는다. 올바른 날짜를 입력하면 계속 진행하고 마지막에 [저장 완료] id=...를 출력한다.

02 · 거래 목록

python -m budget_app list --limit 3

heapq.nlargest()로 고른 거래 날짜 기준 최신 3건과 id: 줄을 확인한다.

03 · 조건 검색

python -m budget_app search --category food

조건에 맞는 거래를 거래 날짜 기준 최신순으로 출력한다.

04 · 월별 요약

python -m budget_app summary --month 2026-09 --top 3

총수입·총지출·잔액·지출 카테고리 TOP을 출력한다.

05 · 예산 연결

python -m budget_app budget set --month 2026-09 --amount 10000
python -m budget_app summary --month 2026-09 --top 3

예산 사용률과 남은 예산 또는 초과 금액이 요약에 추가된다.

06 · 카테고리 관리

python -m budget_app category add

새 이름으로 demo_extra 입력.

python -m budget_app category list
python -m budget_app category remove

삭제 화면에서 demo_extra의 번호를 선택한다. 사용 중 삭제 차단은 food 번호를 선택하면 확인할 수 있다.

07 · 거래 수정

02 거래 목록에서 수정할 거래의 id: 뒤 값을 확인한다. 아래 실제-ID는 그 값으로 바꿔 입력하며, 글자 그대로 실행하지 않는다.

python -m budget_app update --id 실제-ID

새 날짜·종류·카테고리는 Enter로 유지하고 새 금액에 17000 입력. 나머지도 Enter로 유지.

[수정 완료] 뒤 같은 ID의 금액이 바뀐다.

08 · 거래 삭제

수정에 사용한 거래를 삭제한다. 아래 실제-ID도 목록에서 확인한 ID 값으로 바꾸고, 확인 질문에는 y를 입력한다.

python -m budget_app delete --id 실제-ID

[삭제 완료]. 다른 거래는 그대로 남는다.

09 · CSV 내보내기

python -m budget_app export --out demo_export.csv --month 2026-09

--month 2026-09는 2026년 9월 거래만 내보낸다는 뜻이다. 완료되면 [완료] demo_export.csv (N records)를 출력한다.

10 · CSV 가져오기

python -m budget_app import --from import_test.csv

제공된 CSV는 정상 1행·금액 오류 1행이다. imported=1은 저장한 행 수, skipped=1은 오류로 건너뛴 행 수다.

다시 실행하면 정상 행이 새 ID로 한 번 더 저장된다.

CategoryService.remove_category()는 거래를 한 건씩 살펴보고 해당 카테고리가 쓰이면 ValueError를 발생시킨다. 기존 거래의 분류를 보호한다.

›
사용 중인 카테고리는 기존 거래를 보호하기 위해 삭제하지 않는다.

python -m budget_app budget get --month 2026-09

1-5CSV: UTF-8 · 헤더 · 여섯 열

dateYYYY-MM-DD
typeincome / expense
category등록된 이름
amount양수 정수
memo선택 문자열
tags쉼표 구분 문자열

csv_service.py의 CSV_FIELDNAMES가 열 순서를 정한다. DictWriter.writeheader()가 헤더를 쓰고, DictReader가 가져올 파일의 헤더와 필수 열을 검사한다. 양쪽 모두 encoding='utf-8'로 연다. CSV에는 거래 ID가 없어 import할 때 새 ID가 생긴다.

›
CSV는 여섯 열이며 import할 때 새 ID를 만든다.

1-6잘못된 입력과 파일 오류: 메시지·해결 힌트

add의 날짜 오류는 입력 단계에서 먼저 검사해 날짜만 다시 받는다. 그 밖의 입력값 오류는 ValueError, 파일 접근 오류는 OSError로 진입점에 전달되고, safe_entry가 사용자 메시지와 힌트로 바꿔 Python traceback을 직접 보여주지 않는다.

raise ValueError→@safe_entry→wrapper의 except→SystemExit(1)→$LASTEXITCODE = 1
›
add 날짜는 즉시 재입력, 공통 예외는 @safe_entry가 처리한다.

1-7실패 종료 코드

safe_entry.wrapper()는 처리한 오류 뒤 SystemExit(1)로 끝난다. PowerShell의 $LASTEXITCODE는 방금 실행한 Python 프로세스의 종료 값을 보여준다. 정상 명령은 0, 위 잘못된 검색은 1이다.

›
정상 종료는 0, 처리된 오류는 1이다.

모듈의 역할과 데이터 안전

2-1모듈을 나눈 이유와 실행 흐름

① __main__.py + cli.py실행 시작 · 명령 선택 · 화면 입력과 출력
↓
② service.py거래 검증 · 검색 · 요약 · 예산과 카테고리 규칙
↓
③ repository.pyJSONL 파일 읽기 · 한 줄 기록 · 수정·삭제 시 파일 교체
↓
④ data/*.jsonl거래 · 카테고리 · 예산을 재실행 뒤에도 보관
models.py · 데이터 모양Transaction의 id, 날짜, 금액, 태그 등 필드
csv_service.py · 파일 교환CSV 헤더, 내보내기, 행별 검증과 가져오기
decorators.py · 공통 오류 처리@safe_entry가 입력·파일 오류를 안내하고 실패 코드로 종료

모듈은 역할별 코드 파일이다. 화면 문구를 바꿀 때는 CLI, 계산 규칙을 바꿀 때는 Service, 저장 방식을 바꿀 때는 Repository를 중심으로 살핀다.

›
CLI → Service → Repository → JSONL 순으로 흐른다.

2-3update / delete의 파일 교체

with_suffix('.tmp')로 거래 파일 옆에 임시 경로를 만든다.
원본을 한 건씩 읽는다. update는 대상에 수정값을 쓰고, delete는 대상에서 continue로 기록을 건너뛴다.
나머지는 _write_json_line()으로 임시 파일에 쓴다.
대상을 찾았으면 replace()로 완성된 임시 파일을 원본과 교체한다.
대상을 못 찾았으면 unlink(missing_ok=True)로 임시 파일을 정리한다.

실행 전 Service도 ID 존재를 확인한다. 이 방식은 원본을 직접 중간부터 고치는 일을 피하지만, 동시 실행이나 쓰기 중 전원 차단까지 완전히 보장하지는 않는다.

›
임시 파일을 완성한 뒤 원본과 교체한다.

Python 개념을 실제 코드와 연결

3-1Generator · 한 줄 읽기와 정렬 범위

무엇현재 코드메모리 특성
Repository 읽기iter_transactions() -> Iterator[Transaction]가 JSONL을 한 줄씩 읽어 yield파일 전체를 먼저 list로 만들지 않음
listheapq.nlargest(limit, ..., key=date)거래 날짜 기준 최신 N건만 유지
search조건 결과를 matches = []에 모은 뒤 sorted(..., reverse=True)날짜 최신순 정렬 때문에 일치 결과 수만큼 메모리 사용

두 기능 모두 Repository Generator로 파일을 한 줄씩 읽는다. 다만 search는 일치 결과 전체를 모아 정렬하므로 완전한 끝단 스트리밍은 아니다.

›
list는 N건만 유지하고 search는 일치 결과 전체를 모은다.

3-2Decorator · 공통 오류 처리 한 곳에

무엇어떻게왜
함수를 감싸 공통 동작을 붙이는 Python 문법__main__.py의 @safe_entry가 main()을 감싸고, decorators.py의 wrapper()가 대표 예외를 처리명령마다 같은 사용자 오류 문구와 종료 코드를 반복하지 않음
Service: raise ValueError→@safe_entry(main)→wrapper: except ValueError→힌트 출력→SystemExit(1)→$LASTEXITCODE 1

현재 데코레이터의 기능은 오류 처리다. CSV의 깨진 행을 skipped로 세는 일은 CsvService 내부에서 처리한다.

›
@safe_entry는 공통 오류 처리용이며 로깅 기능은 없다.

3-3Type Hint · 입력과 반환의 예상 모양

무엇어떻게왜
값의 예상 타입을 코드에 적는 표기BudgetRepository.get_budget(self, month: str) -> int | None: 월 문자열을 받고 예산 정수 또는 미설정 None 반환함수를 호출하는 사람이 필요한 입력과 결과의 경우를 쉽게 파악
거래의 필드 모양Transaction.tags: list[str] · search_transactions() -> Iterator[Transaction]태그 목록과 순차 결과라는 계약을 코드에서 확인

Type Hint는 Python 실행 중 값을 자동 검사하거나 강제로 바꾸지 않는다. 실제 값 검증은 Service 코드가 맡는다.

›
타입 표기는 예상 자료형을 보여주지만 실행 중 강제 검사는 아니다.

저장 방식 · 규모 · 가져오기 정책

4-1내부 JSONL과 교환용 CSV

형식이 프로그램에서 쓰는 곳장점한계
JSONLdata의 거래·카테고리·예산한 줄에 한 항목, 태그 목록을 그대로 기록, 순차 읽기 쉬움표로 열기 불편, 조건 검색·수정은 파일을 훑거나 다시 써야 함
CSVexport/import 파일표 프로그램과 교환하기 쉬움, 열 구조가 보임태그 목록은 쉼표 문자열로 변환, ID 열은 현재 스키마에 없음

거래 원본은 _write_json_line()으로 저장하고, CSV는 CsvService가 변환한다.

›
JSONL은 내부 저장, CSV는 교환용이다.

4-2거래 10만 건에서 느려지는 곳과 개선

list/search/summary는 조건에 따라 거래 파일 전체를 훑는다. list는 nlargest()로 보관량을 N건으로 제한한다.
search는 일치 결과를 matches 리스트에 모아 정렬하므로 결과가 많으면 메모리도 늘어난다.
update/delete는 한 건 변경에도 거래 파일 전체를 새로 쓴다.
규모가 커지면 SQLite로 옮기고 ID·날짜·카테고리에 인덱스를 두며 결과를 페이지 단위로 조회한다.

인덱스는 책 뒤의 색인처럼 찾을 위치를 빠르게 좁히는 데이터베이스 구조다. SQLite와 인덱스는 현재 구현된 기능이 아니라 개선 방향이다.

›
대용량에서는 SQLite·인덱스·페이지 조회를 검토한다.

4-3깨진 CSV 행: 부분 성공과 skipped

헤더·필수 열 검사→행별 날짜·종류·카테고리·금액 검사→정상: 저장 + imported / 오류: 건너뜀 + skipped

제공된 import_test.csv는 정상 1행과 숫자가 아닌 금액 1행이다. CsvService.import_transactions()는 행 안의 ValueError 등을 잡아 정상 행만 저장한다. 출력은 imported=1, skipped=1이다.

이 정책은 정상 데이터까지 버리지 않지만 일부만 저장된 상태가 된다. 현재는 전체 롤백이나 행 번호·원인별 리포트가 없다. 사용자는 두 건수를 확인하고 원본 CSV를 고쳐 재시도할 때 중복 저장에 주의해야 한다.

›
import는 정상 행만 저장하는 부분 성공 방식이다.
