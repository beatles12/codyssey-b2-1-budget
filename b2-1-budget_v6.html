2-3update / delete의 파일 교체

with_suffix('.tmp')로 거래 파일 옆에 임시 경로를 만든다.
원본을 한 건씩 읽는다. update는 대상에 수정값을 쓰고, delete는 대상에서 continue로 기록을 건너뛴다.
나머지는 _write_json_line()으로 임시 파일에 쓴다.
대상을 찾았으면 replace()로 완성된 임시 파일을 원본과 교체한다.
대상을 못 찾았으면 unlink(missing_ok=True)로 임시 파일을 정리한다.

실행 전 Service도 ID 존재를 확인한다. 이 방식은 원본을 직접 중간부터 고치는 일을 피하지만, 동시 실행이나 쓰기 중 전원 차단까지 완전히 보장하지는 않는다.

›
임시 파일을 완성한 뒤 원본과 교체한다.

Python 개념을 실제 코드와 연결

3-1Generator · 한 줄 읽기와 정렬 범위

무엇현재 코드메모리 특성
Repository 읽기iter_transactions() -> Iterator[Transaction]가 JSONL을 한 줄씩 읽어 yield파일 전체를 먼저 list로 만들지 않음
listheapq.nlargest(limit, ..., key=date)거래 날짜 기준 최신 N건만 유지

두 기능 모두 Repository Generator로 파일을 한 줄씩 읽는다. 다만 search는 일치 결과 전체를 모아 정렬하므로 완전한 끝단 스트리밍은 아니다.

›
list는 N건만 유지하고 search는 일치 결과 전체를 모은다.

3-2Decorator · 공통 오류 처리 한 곳에

무엇어떻게왜
함수를 감싸 공통 동작을 붙이는 Python 문법__main__.py의 @safe_entry가 main()을 감싸고, decorators.py의 wrapper()가 대표 예외를 처리명령마다 같은 사용자 오류 문구와 종료 코드를 반복하지 않음
Service: raise ValueError→@safe_entry(main)→wrapper: except ValueError→힌트 출력→SystemExit(1)→$LASTEXITCODE 1

현재 데코레이터의 기능은 오류 처리다. CSV의 깨진 행을 skipped로 세는 일은 CsvService 내부에서 처리한다.

›
@safe_entry는 공통 오류 처리용이며 로깅 기능은 없다.

3-3Type Hint · 입력과 반환의 예상 모양

무엇어떻게왜
값의 예상 타입을 코드에 적는 표기BudgetRepository.get_budget(self, month: str) -> int | None: 월 문자열을 받고 예산 정수 또는 미설정 None 반환함수를 호출하는 사람이 필요한 입력과 결과의 경우를 쉽게 파악
거래의 필드 모양Transaction.tags: list[str] · search_transactions() -> Iterator[Transaction]태그 목록과 순차 결과라는 계약을 코드에서 확인

Type Hint는 Python 실행 중 값을 자동 검사하거나 강제로 바꾸지 않는다. 실제 값 검증은 Service 코드가 맡는다.

›
타입 표기는 예상 자료형을 보여주지만 실행 중 강제 검사는 아니다.

저장 방식 · 규모 · 가져오기 정책

4-1내부 JSONL과 교환용 CSV

형식이 프로그램에서 쓰는 곳장점한계
JSONLdata의 거래·카테고리·예산한 줄에 한 항목, 태그 목록을 그대로 기록, 순차 읽기 쉬움표로 열기 불편, 조건 검색·수정은 파일을 훑거나 다시 써야 함
CSVexport/import 파일표 프로그램과 교환하기 쉬움, 열 구조가 보임태그 목록은 쉼표 문자열로 변환, ID 열은 현재 스키마에 없음

거래 원본은 _write_json_line()으로 저장하고, CSV는 CsvService가 변환한다.

›
JSONL은 내부 저장, CSV는 교환용이다.

4-2거래 10만 건에서 느려지는 곳과 개선

list/search/summary는 조건에 따라 거래 파일 전체를 훑는다. list는 nlargest()로 보관량을 N건으로 제한한다.
search는 일치 결과를 matches 리스트에 모아 정렬하므로 결과가 많으면 메모리도 늘어난다.
update/delete는 한 건 변경에도 거래 파일 전체를 새로 쓴다.
규모가 커지면 SQLite로 옮기고 ID·날짜·카테고리에 인덱스를 두며 결과를 페이지 단위로 조회한다.

인덱스는 책 뒤의 색인처럼 찾을 위치를 빠르게 좁히는 데이터베이스 구조다. SQLite와 인덱스는 현재 구현된 기능이 아니라 개선 방향이다.

›
대용량에서는 SQLite·인덱스·페이지 조회를 검토한다.

4-3깨진 CSV 행: 부분 성공과 skipped

헤더·필수 열 검사→행별 날짜·종류·카테고리·금액 검사→정상: 저장 + imported / 오류: 건너뜀 + skipped

제공된 import_test.csv는 정상 1행과 숫자가 아닌 금액 1행이다. CsvService.import_transactions()는 행 안의 ValueError 등을 잡아 정상 행만 저장한다. 출력은 imported=1, skipped=1이다.

이 정책은 정상 데이터까지 버리지 않지만 일부만 저장된 상태가 된다. 현재는 전체 롤백이나 행 번호·원인별 리포트가 없다. 사용자는 두 건수를 확인하고 원본 CSV를 고쳐 재시도할 때 중복 저장에 주의해야 한다.
